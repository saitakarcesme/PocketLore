# Durable task runner

`runner.py` is a Linux, standard-library-only supervisor. Its private state, task queue, process logs and frozen critic artifacts live outside Git. A systemd user service owns its process group and survives SSH disconnects; user lingering must be enabled. The service takes an exclusive `flock`, writes JSON with file and directory fsync plus atomic rename, and wakes through inotify when task files arrive.

Task JSON requires `id`, `objective`, `scope`, `dependencies` (task IDs), `acceptance_checks` (argument arrays, never shell strings), and `artifacts` (required file paths). Optional `prompt` gives bounded implementation details. `roles/sessions.json` registers an explicit `builder` session ID; the runner never selects a global latest session. Each critic starts a separate clean persisted session in the evidence directory and receives only goals and immutable task evidence. All actual session IDs are recorded in task state.

The private `runner/config.json` must set `dispatch_enabled` to true before ready tasks execute; the default false permits safe queue review and recovery checks.

A task progresses through builder, validation, critic, checkpoint, and completion. Builder output is not acceptance. Relevant checks plus the independent critic must pass before main advances. Failed changes are preserved and pushed on checkpoint branches. Repairs have explicit task IDs; a third failed approach creates a distinct strategy-change task; a failed strategy-change attempt blocks that branch while independent tasks continue. A repair's acceptance satisfies the original dependency. There is no arbitrary total dispatch limit. External-dependency tasks should remain outside the ready queue until their prerequisite exists; maintain their gaps in the product release list.

Process receipts prevent finished commands from running again after restart. An interrupted builder is resumed by the session ID recovered from its event log, with instructions to inspect existing work first. A process that is killed between its side effect and durable receipt can be repeated: acceptance commands must therefore be idempotent. Systemd must use `KillMode=control-group` so restart cannot leave orphan builders. The runner preserves the working tree during recovery; it never resets or cleans it. A clean working tree is required before a new task starts.

Run checks with `python3 tools/orchestration/test_runner.py`. Run `python3 tools/orchestration/recovery_smoke.py` to inject a real supervised crash after a process receipt but before its completion event; the fixture verifies exactly one execution and one completion. The service's environment sets local toolchain paths; no global Codex configuration is changed. Private service installation and the actual restart smoke test are recorded under the control directory.

## Canonical roles and explicit policies

`roles/sessions.json` is the only live registry. Preserve duplicate initialization IDs as superseded history, never select a global last session. Builder and critic calls both resume their canonical IDs. Persist `approval_policy`, `sandbox_mode`, `add_dirs` and network access under `runner/config.json` → `role_policies`; each task snapshots its effective policies and argv before launch. Only read-only or workspace-write sandboxes are accepted. No blanket bypass flags are used. The critic receives only the immutable review directory and bounty goals; its output contains a machine decision and one English sentence of at most 35 words. The deterministic language guard is conservative and does not prove fluency.

Each completion is replayably projected from runner state into an append-only `state/continuity-ledger.jsonl`, English `context/CURRENT_STATE.md`, and `notifications/pending`. A separate supervised `continuity.py --control PATH` process resumes the canonical continuity chat with exact task, commit, result, next step and event ID. Delivery receipts, retry backoff and completed-turn recovery keep notification failures independent of application work. A notification may be delivered again after an interrupted turn, so event IDs explicitly request idempotent acknowledgment. No builder logs or private planning narrative are passed to the critic.

Repair tasks carry a monotonic `repair_ordinal`: two bounded repairs follow the first failure, then the third failure requires a different approach and a strategy evidence artifact. If that alternative fails, the branch is marked `strategy_exhausted`; this is not falsely described as an external dependency. Independent ready tasks continue. Task ordering always prioritizes an existing running task over pending tasks. Builders may checkpoint meaningful changes on their current checkpoint branch; they must never reset, switch branches or advance main.

Deploy maintenance from a clean isolated worktree. Pin all runtime Python modules and schema by commit/hash under private control, preserve the active task/session/receipt and dirty application files, then restart the service with `KillMode=control-group`. The resumed task keeps its branch and uses the same explicit session ID. Integrate the reviewed maintenance commit through a separate queued task at a safe boundary; never edit the active application checkout during maintenance.
